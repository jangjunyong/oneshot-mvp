# 디자인 변경 계획안 (2026-09-10)

> 사용자 요청: "taste 스킬로 AI 티 제거, 힉스필드나 미드저니로 디자인 변경, 브레인스토밍 스킬로 계획안".

> 근거: 2026-09-10 크롬 클릭 관찰(`docs/design/audit_2026-09-10/`), 설치한 taste-skill 4종(`~/.claude/skills/design-taste-frontend` · `redesign-existing-projects` · `minimalist-ui` · `imagegen-frontend-web`), 개인 디자인 시스템 "도면" v2(`~/.claude/design-system/README.md`).

## 1. 디자인 읽기 (taste §0.B)

**읽기:** 공공기관 심사위원(관광공사 공모전)이 5분 보는 **공공·신뢰 우선 데이터 도구**의 리디자인(보존형). 언어는 "도면·실측·판정"의 절제된 편집형. 실제 디자인 시스템은 이미 있다(도면 v2, 흑백 + 상태색 2). 새 시스템을 들이지 않는다.

**다이얼(taste §1.A "trust-first / public-sector"):** VARIANCE 3~4 · MOTION 2 · DENSITY 4~5. 지금 화면의 다이얼 추정은 VARIANCE 4 · MOTION 1 · DENSITY 5. 즉 **구조는 이미 맞다**. 문제는 구조가 아니라 마감(서체 폴백·장식 라벨·내부 상태 노출)이다.

**정직하게 적어 둘 것:** taste-skill 본체는 스스로 "랜딩·포트폴리오·리디자인용. 대시보드·데이터 표·다단계 제품 UI는 아니다"라고 선언한다. 이 제품의 여섯 화면 중 랜딩 성격은 `/` 하나뿐이고 나머지는 데이터 UI다. 그래서 taste 본체는 `/`의 첫 화면과 문구·라벨 규율에, `redesign-existing-projects`의 감사 목록은 나머지 다섯 화면에 쓴다. 모션 라이브러리(Motion)·아이콘 라이브러리(Phosphor) 같은 taste의 기본 스택은 **불문율 "새 의존성 0"에 막혀 쓰지 않는다**. CSS만으로 한다.

## 4. A의 작업 명세 (승인 시 그대로 실행)

1. **서체(T1·T2).** `--font-mono` 폴백 사슬에 KR 글리프 서체를 끼운다: `var(--font-mono-loaded), "IBM Plex Mono", var(--font-body-loaded), "IBM Plex Sans KR", monospace`. 브라우저는 글자 단위로 폴백하므로 숫자·라틴은 Plex Mono, 한글은 Plex Sans KR로 찍힌다. `layout.tsx`의 `IBM_Plex_Sans_KR`에 `subsets: ["korean", "latin"]`을 시도한다(next/font가 한글 subset을 슬라이스로 지원하는지 빌드로 확인. 안 되면 `Noto Sans KR`로 교체). `.report h2`는 `--font-display` 대신 본문 서체 500 weight. 기계 검사: `lib/copy.test.ts`에 "mono 사슬에 KR 서체가 있다" 1건.
2. **내부 상태 노출(T3·T4·T12).** `/`·`/venue` 표제란에서 STORAGE·ENTRY·SCALE·ITEMS 행을 지우고 PROJECT를 "기획안 팩트체크"로. 모델명·쿼터 문구는 "문서에서 숫자를 옮겨 적는 데만 모델을 씁니다. 판정에는 쓰지 않습니다"로 바꾸고 모델명은 `title` 속성으로 내린다. 기계 검사: `grep -rn "DATABASE_URL\|연결 없음\|미지정" app/` 0건.
3. **라벨 다이어트(T6·T7·T9).** `grid-ref`는 화면당 1개(이미 그렇다), 가운뎃점은 한 줄 1개로 줄이고 나머지는 줄바꿈·헤어라인. 표제란 4열 대문자 라벨은 2열(출처·조회일)로. `.dim` 치수선은 실제 구역 전환(입력 → 판정)에만 남긴다.
4. **em-dash(T5).** 산문은 이미 0건. 절 제목의 "—"는 §7의 결정에 따른다. 바꾼다면 마침표 또는 헤어라인.
5. **곡선 라벨(T10).** "평소 73k" 텍스트를 점선 위 오른쪽 끝으로 옮기고 흰 배경 패딩.
6. 회귀: `npm run lint && npm run typecheck && npm test && npm run build && npm run test:e2e`. e2e 요약 줄을 눈으로 읽고 커밋.

## 5. B에서만 하는 것 (미드저니·힉스필드)

이미지 생성은 사용자의 수동 작업이다. 나는 프롬프트와 자리·규격을 주고, 받은 파일을 넣는다.

- **자리 3곳뿐.** `/` 첫 화면 오른쪽 여백(현재 비어 있는 640px 폭), `/report`·`/report/check` 1장 상단 얇은 띠(인쇄 흑백에서도 읽히는 선화), 기능설명서 표지. **근거 화면(`/evidence`·판정표·`/venue` 지도)에는 넣지 않는다.** 실측 옆의 생성 이미지는 "가짜 사진"으로 읽힌다.
- **스타일 잠금(imagegen §16):** 단색 선화(잉크 스케치), 흰 바탕, 유채색 0, 도면·측량·지진계 모티프. 사진풍 금지, 사람 얼굴 금지(초상·저작권), 특정 축제 실사 재현 금지.
- **프롬프트 초안(미드저니):** `minimal continuous-line ink drawing of a festival ground survey map with a single seismograph needle trace, architectural drawing sheet, white paper, black ink only, no color, no people, no text, generous negative space --ar 3:2 --style raw --v 7` / 힉스필드는 같은 문장에 "still image, no motion".
- **표기:** 이미지 아래 캡션 "생성 삽화(AI). 자료가 아닙니다". 기능설명서 §3 데이터 절에 삽화 출처 한 줄.
- **작업량:** 프롬프트·검수 0.3일 + 배치·캡션·회귀 0.4일 + `/` 재구성 0.8일 = 1.5일(A 포함).

## 6. 바꾸지 않는 것 (taste §11.F)

URL·라우트, 나침반 라벨(M4에서 막 정한 것), 폼 필드 이름(e2e·URL 계약), 로고 "기획안 팩트체크", 판정·구간·시뮬 코드 전부, `<Num>` 출처 셀 규약, 문구의 화자·단정 규율.

## 7. 사용자가 정할 것

1. **A / B / C 중 무엇으로 가는가.** 추천은 "A 지금, B는 M12 뒤".
2. **절 제목의 em-dash를 없앨 것인가.** taste는 0건, HANDOFF는 허용. 추천은 없애기(마침표로). 근거: 심사위원이 보는 화면에서 LLM 티가 가장 자주 지적되는 문자다.
3. **"이런 느낌" 참고 이미지.** `docs/design/refs/`에 넣어 주면 §3의 C 방향을 그 기준으로 다시 잰다. 없으면 C는 열지 않는다.
4. **AI 생성 삽화를 제출물에 쓸 것인가.** 공모전 규정(제출양식)에 생성물 표기 조항이 있는지 사용자가 확인해야 한다. 볼트에는 없음.
