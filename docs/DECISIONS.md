## 2026-08-30 — 도면을 접고 축을 옮긴 날

이날 하루에 방향이 두 번 뒤집혔다. 둘 다 **추측이 아니라 측정과 조사가 뒤집었다.**

### 1) 도면 확장 → 동결

**하던 것.** "부지에 맞춰 보기"(뷰 배율·타일 오버줌)를 만들어 배포했다(`f79a9f5`). 다음은 치수 입력·임의 폴리곤 구역·밑그림 강화였다.

**멈춘 이유.** 사용자가 물었다 — "주차장 부스 등 시설이 왜 죄다 사각형이냐, 이거 대행사가 할 일을 우리가 만드는 거 아니냐."

조사해서 확인했다.

- **2026 해운대 모래축제 행사대행 용역 과업내용서**(g2b 공고문 원문)에 부스 규격·동선·안전관리요원 배치가 전부 **대행사 과업**으로 박혀 있다. 필수 부스가 `자원봉사 운영본부 3×9`, `구 상황실·축제평가 각 5×5`, `의료부스 3×3` 처럼 **m 단위 사각형으로 발주**된다.
- 배치도를 그리는 주체는 지자체 담당자가 아니라 **대행사**다. 담당자는 받아서 심의에 올린다.
- 행안부 「지역축제장 안전관리 매뉴얼(2024)」 부록2 표준안에 "배치도 및 평면도" 칸이 있고, 표시할 요소(종합안내도·무대·조명·스피커·좌석·관람객 진출입구·안전관리요원·비상시 안내로·울타리·소방차 진출입구·소화기 등)가 법으로 정해져 있다. 안전관리계획은 **순간 최대인원 500명↑ 수립 / 1,000명↑ 심의**.

**결정.** `/venue`·`lib/venue.ts`·`lib/scan.ts`·`lib/tilemap.ts` **동결.** 지우지는 않는다(구현성 점수·데모 가치). 진단서의 "근거 3"으로만 남긴다.

**부수 발견 — 우리가 채울 구멍이 어디인지.** 매뉴얼 128쪽 전체에 **통로 폭·밀집도(㎡당 명)·수용인원 산출식이 하나도 없다.** 그런데 심의 착안 사항(부록3)은 "예상인원 **수용 여부**"와 "관람객 **동선**"을 묻는다. 담당자는 근거 없이 숫자를 적고 심의위원은 근거 없이 통과시킨다. 이 구멍이 제품의 자리다.

### 2) 물량 환산표 → 데이터가 반증해서 폐기

**하려던 것.** `필요 물량 = 작년 물량 × 쌍둥이 실측 배수`. 예: 작년 화장실 10개 × 2.58배 = 26개. "예산 낭비"에 직접 답하는 그림이었다.

**틀린 이유 (직접 측정).** `actualVisitSurge` 의 분모는 **평상시 그 시군구**지 *작년 그 축제*가 아니다(`lib/types.ts:29`). 두 비율의 분모가 다른데 곱했다.

619건 전수로 `쌍둥이 중앙 배수 ÷ 본인 실측 배수` 를 재니:

```
p05 0.71 · p25 0.91 · 중앙 1.00 · p75 1.10 · p95 1.33
1.0 미만 49%   |   1.2 초과 14%
```

고령군 담당자 화면에서 이런 자가당착이 난다.

> 근거 1: 고령 대가야축제가 **평소의 2.27배**였습니다
> 근거 5: 작년 화장실 10개 → **26개** 필요

작년에 2.27배를 10개로 치른 기록을 근거로 내밀면서 26개를 요구한다. 올바른 비는 `2.58 / 2.27 = 1.14` → 12개다. 계획대로면 **2.2배 과잉**이고, **예산 낭비를 막겠다는 제품이 예산 낭비를 생산한다.**

**그리고 우리 자신의 eval 을 깬다.** `evals/cases.md` 09행: *"화면의 숫자가 전부 입력값·지역 인구·실측 배수·연도 중 하나인가."* "26개"는 네 범주 어디에도 없는 다섯 번째 숫자다. 같은 파일이 "09가 제일 중요하다"고 못 박아 뒀다.

**결정.** 물량 **개수를 출력하지 않는다.** 대신 배수 비율 구간만 낸다(`lib/capacity.ts`) — "작년이 감당한 수준의 0.78~1.45배 구간". 첫 회 축제에도 뜨고, eval 09 를 통과한다.

### 3) 시기 감도 표 → 이름이 거짓이라 표시를 고침

**하려던 것.** 달만 바꿔 `findSimilar` 를 12번 돌려 "3월에 열면 2.58배, 9월이면 1.42배" 표.

**틀린 이유 (직접 측정).** 요청한 달에 **실제로 열린** 쌍둥이 비율:

```
고령 7/36 = 19%   ·   마포 7/36 = 19%

"9월 요청" → 쌍둥이 실제 개최월 [10, 10, 8]   ← 9월 축제가 한 곳도 없다
"1월 요청" → 쌍둥이 실제 개최월 [10,  3, 4]
```

`month` 가중치는 0.1(`lib/match.ts:14-20`)이라 12번 돌려도 같은 지역 축제 4~5개가 재배열될 뿐이다. "3월에 열면"이라고 쓰면 거짓말이다.

**결정.** 기능은 살리되 **이름과 표시를 고친다.** 이 표는 *시기의 효과*가 아니라 **매칭의 시기 민감도**를 잰다. 각 행에 **쌍둥이 실제 개최월**을 찍어 19%를 화면에 드러낸다. 표가 스스로 한계를 말하게 한다.

### 4) `flat` 판정 → 임계값을 숨긴 설계라 바꿈

"임의 임계값을 안 쓴다"며 **"12달 등급이 전부 같은가"** 로 평평함을 판정하려 했다. 그러면 `GRADE_CUT`(2.0/1.5)이 곧 숨은 임계값이 된다. 전수 측정:

```
flat=true  457건  spread 중앙 0.13  최대 0.46 (정읍사문화제)
flat=false 162건  spread 중앙 0.48  최소 0.07 (YES!키즈존)
```

**변동폭이 6.5배 큰 쪽이 "평평"으로 나온다.** → `spread` 기반으로 바꾼다. 컷을 안 끌어들이면 컷의 벼랑도 없다.

### 5) 시연 사례가 `limit=3` 의 부산물이었다

고령 조건에서 `findSimilar` 의 `limit` 만 바꾸면:

```
limit=3 → 9월 근거없음   (시연에서 쓰려던 "3월 심각 vs 9월 근거없음")
limit=5 → 9월 주의       (뒤집힌다)
```

3개짜리 표본의 중앙값이라 한 건 교체가 등급을 넘긴다. **결정:** `robust` 플래그를 둬서 limit 3·5·7 이 일치할 때만 신호로 인정한다.

2. **비평 에이전트를 붙여 계획을 무너뜨리게 했다.** 지적 중 치명적인 둘(시기 표의 요청월-실제월 19% 불일치, `flat` 이 임계값을 숨긴 설계)은 **내가 직접 재서 사실임을 확인**하고 반영했다. 나머지 지적도 대부분 수용했다.

3. **`app/report/page.tsx` 의 중앙값 중복을 고쳤다.** `grade.ts` 는 짝수 개일 때 위쪽 값(보수적)을 쓰는데 진단서는 아래쪽을 썼다. 쌍둥이가 2곳일 때 **같은 문서 안에서 등급과 쏠림 스캔이 다른 배수**를 쓰던 버그다. `g.medianSurge` 를 쓰게 했다.
   - **미해결**: `app/venue/page.tsx` 에도 같은 복제가 있다. 도면 동결 규칙을 지키려고 안 건드렸다. 동결을 풀 때 같이 고칠 것.

4. **검색량을 화면에 안 붙였다.** 사용자가 "전부 진행해"라고 했지만 ① 키가 없어 검증이 불가능하고 ② 상관도 모르는 숫자를 올리면 불문율 4번을 어긴다. 순수 함수 + eval 스크립트까지만 만들었다. 키를 넣고 `evals/search-volume.mjs` 를 돌리면 판정이 나온다(|ρ| < 0.3 이면 버린다).

5. **`evals/cases.md` 의 검증 숫자를 갱신했다.** 2.2배·51.9%·47.9% 는 임계값 0.35→0.27 재보정 전 값이라 낡아 있었다. 현재 2.41배·56.8%·54.1%.

6. **기능설명서 초안을 썼다**(`docs/기능설명서.md`). 비평가가 "심사위원은 코드를 안 읽는다, 구현성 30 + 기획력 30 을 전달하는 건 문서다"라고 지적했고 HANDOFF 에도 계속 밀린 항목이었다. **공모전 제출 양식을 못 받아 자유 양식으로 썼다** — 양식이 오면 옮겨야 한다.

7. **push 하지 않았다.** 검증은 전부 초록(유닛 137 · e2e 7 · typecheck · lint · build)이지만, 자는 동안 배포본이 죽으면 되돌릴 사람이 없다. 아침에 확인하고 `git push origin main` 하면 Vercel 이 배포한다.

```
테마 0.20        정밀도 58.3% · 재현율 52.7% · 리프트 2.47
테마 0.30 (필수)  정밀도 58.0% · 재현율 52.1% · 리프트 2.46
```

**테마를 필수로 만들면 오히려 나빠진다** — 임계값(0.27)보다 큰 가중치를 주면 테마 하나 다르다는 이유로 탈락시키게 되고, 진짜 닮은 축제까지 버려 재현율이 떨어진다. 사용자 직관은 방향이 맞았지만 답은 필수화가 아니라 적당히 올리기였다.
회귀 테스트 2개를 박았다(되돌리면 나빠짐 / 가중치 합 1 이고 테마가 임계값을 안 넘음).

**② "평소대비 2.7배 이러면 이게 먼 소린지 잘 모르겠음"** → 정의를 화면에 박았다

분모가 뭔지 화면 어디에도 없었다. 이제 결론 바로 아래에 적는다 —
*"평소 대비란 축제 기간에 그 시군구를 찾은 **외지인 방문자**가 평상시의 몇 배였나입니다(KT 이동통신 실측). 방문객 총수가 아닙니다."*

**③ "이 구조는 그냥 인구수 적은 지역은 높게 뜰 확률이 올라감"** → 사실이었다

```
인구  ~3만   19건  배수중앙 1.84  심각 37% · 주의 42% · 근거없음 21%
인구 3~6만   83건  배수중앙 1.57  심각 24% · 주의 34% · 근거없음 42%
인구 6~12만  95건  배수중앙 1.38  심각  9% · 주의 29% · 근거없음 61%
인구 12~30만 168건 배수중앙 1.27  심각  2% · 주의 14% · 근거없음 85%
인구 30~100만 233건 배수중앙 1.23 심각  1% · 주의  7% · 근거없음 92%
인구 100만+   21건 배수중앙 1.27  심각  0% · 주의  5% · 근거없음 95%
log(인구) vs 배수  r = -0.486
```

등급이 사실상 인구 프록시다. 소도시는 "우린 늘 심각"이라 무시하고, **대도시에서는 제품이 아무 말도 못 한다(95% 근거없음).**

**배수는 보정하지 않았다.** "평상시의 2.7배"는 물리적 사실이고, 인구로 나눠 만든 새 지표는 실측이 아니라 지어낸 숫자다. 등급 컷도 지역마다 안 바꾼다 — 같은 2.0배가 어디서든 같은 뜻이어야 담당자끼리 말이 통한다.
대신 **또래 맥락**을 더했다(`lib/peer.ts`): "같은 규모(인구 3~6만) 축제 83곳 중 상위 5%, 또래 중앙값 1.57배". 619건에서 세면 나오는 사실이지 새 숫자가 아니다. 표본 수(n)를 항상 같이 낸다 — n=19 에서 "상위 5%"는 1등이라는 뜻이다.

**④ "지도 왼쪽 아래 비는데 이 공간 잘 활용하면"** → 또래 분포 띠(`app/peer-strip.tsx`)

왼쪽 열이 지도 높이에서 끝나 아래가 비어 있었다. 눈금 하나가 또래 축제 한 곳, 등급 컷과 또래 중앙값이 선으로, 이 기획안만 굵고 붉다. ③의 "상위 5%"를 그림으로 되풀이한다. 차트 라이브러리 없음.

**⑤ "위성 지도의 필요성 잘 못 느끼겠음"** → 토글 제거

`tilemap` 의 satellite 스타일은 남긴다(지우면 `ZOOM_LIMITS` 의 실측 근거가 깨진다). 전에 위성으로 저장한 도면은 **불러오는 자리에서** 도면 스타일·z18 로 정규화한다 — 안 그러면 백지도 상한을 넘어 빈 캔버스가 뜬다.

**⑥ "사용자가 도면 세팅하기 어려워하는 것 같은데 기본 도면이라도"** → 예시 배치(`lib/preset.ts`)

"부지 지도 깔기" 한 번에 200×140m 예시 16개(무대·부스 8·화장실 2·출입구 2·주차장·주 동선)가 같이 깔린다. 누르는 즉시 부지 28,000㎡ 가 뜨고 스캔이 "부스 3 부하 6.7×"라고 말한다.
**예시도 실측이다** — 크기는 전부 `KIND_SIZE_M` 에서 나오고, 면적·경계 안·이름 중복을 테스트가 지킨다. 부스 인력/선호도는 일부러 고르지 않게 뒀다(다 같으면 스캔이 아무 말도 안 한다).
"평수가 중요한 게 아닌 것 같다"는 지적은 면적 표시를 **안 지웠다** — 부지 면적은 경계 밖 판정과 감당 범위의 입력이라 빼면 스캔이 죽는다. 대신 예시가 깔리며 자동으로 채워져 담당자가 잴 일이 없어졌다.

### 사용자가 반려한 것
