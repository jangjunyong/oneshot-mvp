# FLOW — 흐름 · 실패 경로 · 도구 선택

## 1. 판정: 함수인가 워크플로우인가 에이전트인가

**에이전트다.** 다만 **처음 설계는 아니었고**, 그걸 알아채고 바꾼 결과다.

### 이전 설계가 왜 워크플로우였나 (기록)

처음엔 "보유 종목 사이의 경로를 찾는다"였다. 근거는 *"탐색 경계가 커지니 어디를 펼칠지 골라야 한다"* 였는데 — **그건 배치 단계 얘기였다.** `graph.json`을 굽는 스크립트고, 스크립트는 에이전트가 아니다.

런타임에 남는 걸 세어보니 전부 결정적이었다.

| 상황 | 런타임 | 선택의 여지 |
|---|---|---|
| 커버리지 안 종목끼리 | 사전 그래프 BFS | 없음 (API 0콜) |
| 커버리지 밖 종목 | 최대주주·출자 조회 | 없음 (2~3콜 고정) |
| 최근 지분 변동 | 대량보유 조회 | 없음 |

**사전에 잘 구울수록 런타임이 결정적이 된다.** 두 목표가 상충하는데 둘 다 챙기려다 에이전트가 죽었다.

### 지금 설계가 에이전트인 이유

질문을 바꿨다 — *"구조가 어떻게 되나"* 에서 **"왜 같이 떨어졌나"** 로. 원인이 하나가 아니라서 **가설 검증 루프**가 된다.

**모델이 정하는 것**
- 어느 가설부터 볼지
- 각 가설을 **얼마나 깊이** 팔지 — 3홉까지 갈지, 커버리지 밖 회사를 온디맨드로 수집할지
- 증거가 충분한지, 더 팔지
- 증거가 여럿일 때 **무엇이 주 원인인지**

가설 1에서 강한 증거가 나오면 나머지를 얕게 보고 끝낸다. 약하면 더 판다. 종목 3개면 두 가설로 끝나고 8개면 조합이 많아 더 봐야 한다. **첫 조회 결과가 다음 행동을 정하므로 실행 전에 호출 순서를 그릴 수 없다.**

**모델이 못 정하는 것 (규칙)**
- 근거 없이 원인 단정 — 공시 항목으로 못 짚으면 말하지 않는다
- **가설 4(시장 전체)를 건너뛰기** — 값 하나 조회라 싸다. 항상 본다. *순서는 자유*
- 최대 스텝 초과

> 정직하게: agency의 대부분은 **가설 1의 깊이 조절**에 있다. 가설 2·3·4는 각각 1~2콜로 싸서 고를 것이 적다. 이 편중이 심하면 다시 워크플로우로 기운다 — Day 3~4에 확인한다.

### 판정 재확인 (Day 3~4)

우기지 말고 잰다.

> 실제 입력으로 돌렸을 때 **가설 1의 조회 깊이가 입력마다 달라지는가.**
> - 항상 같은 깊이로 끝난다 → 고정 단계다. **워크플로우로 전환**
> - 입력에 따라 2콜에서 수십 콜까지 갈린다 → **에이전트가 정당하다**

결과는 이 절에 **날짜와 숫자로** 덮어쓴다. 워크플로우가 맞다고 나오면 그렇게 바꾼다 — *"쓰지 않기로 판단하는 것도 설계입니다."*

## 2. 정상 경로

```
[사용자] 보유 종목 3~8개 입력
   │
   ▼
[종목명 → corp_code 해석]  ── 모호하면 ─▶ 후보 제시하고 되물음
   │
   ▼
┌────────── 에이전트 루프 (최대 8스텝) ──────────┐
│ 상태: 검증한 가설[] · 모은 증거[] · 스텝 수     │
│                                                │
│  모델 판단: 다음에 어느 가설을 볼까?             │
│    ├ 1 지배구조   → 사전 그래프 탐색            │
│    │                (부족하면 온디맨드 수집)     │
│    ├ 2 공동 대주주 → 대량보유 조회              │
│    ├ 3 같은 업종   → 기업개황 조회              │
│    └ 4 시장 전체   → 지수 대비 등락 (항상 1회)   │
│         │                                      │
│         ▼ 증거 평가 — 강한가? 더 팔까?          │
│         └── 충분하면 종료 / 아니면 다음 가설     │
└────────────────────────────────────────────────┘
   │
   ▼
[원인 문장] + [근거 목록] + [확인한 범위]
```

**상태는 셋만** 들고 다닌다 — `검증한 가설[]` · `모은 증거[]` · `스텝 수`.
가설 1을 팔 때만 부가 상태가 붙는다 — `방문한 corp_code Set`.

## 3. 실패 경로

강의 p26: *"에이전트 설계의 대부분은 실패 설계입니다. 정상 경로는 원래 쉽습니다."*

| 이런 일이 생긴다 | 정해두지 않으면 | 이 제품의 처리 |
|---|---|---|
| **원인을 못 찾음** | 그럴듯하게 지어냄 | **"원인 못 찾음"** + 확인한 범위 명시(`가설 1·2·4 확인함`). 근거 없는 단정 0건 |
| **증거가 약한데 단정함** | "계열 때문입니다"로 몰아감 | 증거 강도를 같이 낸다. 약하면 **"~일 수 있습니다"** 로 낮춘다 |
| **DART/시세 API 타임아웃** | 전체가 멈춤 | 1회 재시도 → 실패 시 **그 가설만 "확인 못 함"** 으로 두고 나머지로 답한다 |
| **같은 가설을 반복 검증** | 토큰만 쓰며 무한 루프 | `검증한 가설[]` + **최대 8스텝** |
| **입력이 예상을 벗어남** | 500으로 끝남 | 종목명 모호("한국전력"?) → 후보 제시하고 되물음. 1종목만 → "관계는 2개부터". 커버리지 밖 → 온디맨드 시도 후 안내 |

추가로 정해둔 것:
- **API 키 없음/만료** → 500이 아니라 "DART 키 설정 필요" 안내
- **응답은 왔는데 필드가 빔** → "관계 없음"이 아니라 **"확인 불가"** 로 구분해 기록
- **막히면** — 선택지가 3개 이상이면 멈추고 사용자에게 묻는다

## 4. 프레임워크: 쓰지 않는다

랭체인·랭그래프 없이 **SDK 직접 호출 + while 루프 하나**로 간다. 강의 p24 기준 판정.

| 살 만한 순간 (p24) | 이 프로젝트 |
|---|---|
| 재시도·체크포인트·중단 후 재개가 필요할 때 | 재시도 1회뿐. 한 요청이 수 초 안에 끝난다 |
| 노드가 5개를 넘고 상태가 노드 사이를 흐를 때 | 가설 4개지만 **상태는 3개**고 노드 사이를 흐르지 않는다 |
| 사람이 중간에 개입해야 할 때 | 되물음 1회 |

**셋 다 해당 없음 → 안 산다.** 도구 호출을 받아 `switch`로 분기하고 결과를 다시 넣는 루프면 충분하고, **이 코드는 내가 읽을 수 있다.**

## 5. RAG: 쓰지 않는다

문서를 검색해 답을 만드는 구조가 아니다. **정형 API의 필드를 그대로 읽어 증거로 만든다.** 임베딩·벡터DB·청킹이 들어갈 자리가 없다.

강의 p25가 지적한 RAG 실패 3종(문서에 답이 없음 · 청킹이 답을 자름 · 메타데이터 없어 엉뚱한 문서가 옴)이 **구조적으로 발생하지 않는다.** 증거마다 `보고서·연도·항목`이 그대로 출처로 남는다.

사업보고서 **본문** 파싱은 `PRD.md`의 "안 만들 것"에 있다.

## 6. 도구

| 도구 | 쓰는 가설 | 비고 |
|---|---|---|
| `기업개황` | 1·3 | corp_code 해석 · `induty_code` |
| `공시검색` | 1 | 어떤 보고서가 있는지 |
| `최대주주 현황` | 1 | 지배 관계 |
| `타법인 출자현황` | 1 | 출자 관계 |
| `대량보유 상황보고` | **2** | 5% 이상 보유. **기관투자자는 그래프 노드에서 제외**, 문장으로만 |
| `임원·주요주주 소유보고` | 2 | |
| `기간 등락률` | **4** | ⚠️ **DART 아님.** 공공데이터포털 시세 API 후보 — Day 2에 실제 응답 확인. 슬라이스 4에서 붙인다 |

앞의 넷은 사전 배치에도 쓰고, `대량보유`·`등락률`은 **런타임 전용**이다.

**슬라이스 1~3 동안 가설 4는** 시세 소스가 없으므로 *"시장 전체 하락 여부는 아직 확인하지 않습니다"* 라고 **명시**한다. 조용히 빠뜨리지 않는다.
