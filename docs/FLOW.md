# FLOW — 흐름 · 실패 경로 · 도구 선택

## 1. 판정: 함수인가 워크플로우인가 에이전트인가

**에이전트다.**

판정 시험은 *"실행 전에 도구 호출 순서를 그릴 수 있는가"* 이고, 여기서는 **못 그린다.** 들어온 종목이 사전 그래프에 있는지, 첫 조회에서 무엇이 나오는지에 따라 다음 호출이 매번 달라진다.

| 설계 | 판정 |
|---|---|
| 사전 `graph.json` 조회해서 그려주기 | 함수 |
| `if (경로없음) 대량보유조회()` 를 코드로 | 워크플로우 |
| **모델이 "더 팔지 / 어디를 팔지 / 언제 없음이라 할지" 결정** | **에이전트** ← 이것 |

분기가 코드가 아니라 모델 안에 있다.

## 2. 정상 경로

```
[사용자] 보유 종목 3~5개 입력
   │
   ▼
[종목명 → corp_code 해석]  ── 모호하면 ─▶ 후보 제시하고 되물음
   │
   ▼
[사전 graph.json 에서 경로 탐색]  ⚫지배·계열 · 🟢출자 · 최대 3홉
   │
   ├── 경로 있음 ──────────────────────────▶ 그리고 종료
   │
   ▼ 경로 없음
┌──────────── 에이전트 루프 (최대 6스텝) ────────────┐
│  모델 판단: 멈출까, 더 팔까? 어디를?               │
│    ├ 대량보유 상황보고 조회        (🔵 간선)       │
│    ├ 최대주주 변동 이력 조회       (⚫ 간선)       │
│    ├ 타법인 출자현황 조회          (🟢 간선)       │
│    └ 커버리지 밖이면 corp_code 찾아 온디맨드 수집  │
│         │                                          │
│         ▼ 새 간선 발견 → 그래프에 추가 → 재탐색    │
└────────────────────────────────────────────────────┘
   │
   ▼
[클러스터 판정]  🔴 동일산업 제외하고 연결요소 계산
   │
   ▼
[출력] 그래프 · 진단 문장 · 간선별 공시 출처 · 에이전트 작업 로그
```

**상태**는 세 개만 들고 다닌다 — `발견한 간선[]` · `방문한 corp_code Set` · `스텝 수`.

## 3. 실패 경로

강의 p26: *"에이전트 설계의 대부분은 실패 설계입니다. 정상 경로는 원래 쉽습니다."*

| 이런 일이 생긴다 | 정해두지 않으면 | 이 제품의 처리 |
|---|---|---|
| **모델이 관계를 못 찾음** | 그럴듯하게 지어냄 | **"관계 없음"** 반환 + 확인한 범위 명시 (`대량보유·최대주주변동 조회함`). 근거 없는 간선은 0개 |
| **DART API가 죽거나 시간 초과** | 전체가 멈춤 | 1회 재시도 → 실패 시 **사전 그래프 결과만으로 축소 응답** + "일부 확인 실패" 배지 |
| **같은 회사를 반복 조회** | 토큰만 쓰며 무한 루프 | **최대 6스텝** + `방문한 corp_code Set` 으로 차단 |
| **입력이 예상을 벗어남** | 500으로 끝남 | 종목명 모호("한국전력"?) → **후보 제시하고 되물음**. 1종목만 입력 → "관계는 2개부터" 안내. 코스피200 밖 → 온디맨드 시도, 그래도 없으면 안내 문구 |

추가로 정해둔 것:

- **API 키 없음/만료** → 500이 아니라 화면에 "DART 키 설정 필요" 안내
- **응답은 왔는데 필드가 빔** → 빈 값은 "관계 없음"이 아니라 "확인 불가"로 구분해서 기록
- **막히면** — 선택지가 3개 이상이면 멈추고 사용자에게 묻는다

## 4. 프레임워크: 쓰지 않는다

랭체인·랭그래프를 **쓰지 않고** SDK 직접 호출 + 함수 몇 개로 간다. 강의 p24 기준으로 판정한 결과다.

| 살 만한 순간 (p24) | 이 프로젝트 |
|---|---|
| 재시도·체크포인트·중단 후 재개가 실제로 필요할 때 | 재시도는 1회뿐. 체크포인트 불필요 — 한 요청이 수 초 안에 끝난다 |
| 노드가 5개를 넘고 상태가 노드 사이를 흐를 때 | 노드 사실상 2개(탐색·조회). 상태는 3개뿐 |
| 사람이 중간에 개입해야 하는 흐름일 때 | 되물음 1회. 그 외 개입 없음 |

**셋 다 해당 없음 → 안 산다.** 치를 값(추상화 뒤가 안 보임 · 버전이 바뀌어 에이전트가 옛 문법을 씀 · 학습 시간이 2주에서 빠져나감)만 남는다.

에이전트 루프는 도구 호출을 받아 `switch`로 분기하고 결과를 다시 넣는 **while 루프 하나**로 충분하다. 이 코드는 내가 읽을 수 있다.

## 5. RAG: 쓰지 않는다

문서를 검색해 답을 만드는 구조가 아니다. **정형 API의 필드를 그대로 읽어 간선으로 만든다.** 임베딩·벡터DB·청킹이 들어갈 자리가 없다.

이게 오히려 이 설계의 강점이다 — 강의 p25가 지적한 RAG 실패 3종(문서에 답이 없음 · 청킹이 답을 자름 · 메타데이터가 없어 엉뚱한 문서가 옴)이 **구조적으로 발생하지 않는다.** 간선마다 `보고서·연도·필드`가 그대로 출처로 남는다.

사업보고서 **본문** 파싱은 `PRD.md`의 "안 만들 것"에 있다. 정형 API로 안 되는 건 2주 안에 하지 않는다.
