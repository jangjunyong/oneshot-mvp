# FLOW — 흐름 · 실패 경로 · 도구 선택

## 1. 판정: 함수인가 워크플로우인가 에이전트인가

**슬라이스 1은 함수다. 그리고 그게 맞다.**

강의 p22~23이 명시했다 — *"2주 MVP는 대부분 여기(함수)에 해당합니다."* · *"모르겠으면 함수부터 시작하세요."*

| 설계 | 판정 |
|---|---|
| 기획안 → 거리 계산 → 닮은 축제 N개 → 경보 등급 | **함수** ← 슬라이스 1 |
| `if (닮은축제 == 0) 조건완화후재탐색()` 을 코드로 | 워크플로우 |
| 모델이 "어느 위험축부터 볼지 / 얼마나 팔지" 결정 | 에이전트 ← 슬라이스 2에서 판정 |

### LLM 이 반드시 필요한 두 곳

함수 안에서도 LLM 없이는 안 되는 지점이 있다.

1. **자연어 기획안 파싱** — 실무자는 폼을 채우지 않고 기획안 문서를 통째로 가져온다. 거기서 지역·시기·테마·예상 규모를 뽑는 건 규칙으로 안 된다
2. **보완점 문장 생성** — "닮은 축제 3곳이 전부 물량이 2일차에 소진됐다"를 실무자가 바로 쓸 수 있는 문장으로 옮기는 것

둘 다 **1회 호출**이다. 루프가 아니다. 그래서 아직 에이전트가 아니다.

### 에이전트가 될 수 있는 지점 (슬라이스 2)

축제 위험은 축이 여럿이고, **기획안마다 문제되는 축이 다르다.**

```
기획안
 ├ 축1 수요 과소추정   → 닮은 축제의 예상 vs 실제
 ├ 축2 물량 부족       → 닮은 축제의 소진 시점
 ├ 축3 접근성·동선     → 지역 교통·주차 데이터
 ├ 축4 시기 충돌       → 같은 주말 인근 대형 축제
 └ 축5 기획안의 낙관   → 텍스트에 근거 없는 단정이 섞였나
```

어느 축부터 볼지, 증거가 약할 때 더 팔지, 언제 "이게 주 위험이다"라고 할지를 **모델이 정하면** 에이전트가 된다.

### 판정 방법 (Day 5~6)

우기지 말고 잰다.

> 실제 기획안 여러 개로 돌렸을 때 **모델이 보는 축의 개수와 순서가 입력마다 달라지는가.**
> - 항상 5개를 같은 순서로 본다 → 고정 단계다. **워크플로우로 확정**
> - 입력에 따라 2개에서 5개까지 갈리고 순서도 바뀐다 → **에이전트가 정당하다**

결과는 이 절에 **날짜와 숫자로** 덮어쓴다. 워크플로우가 맞다고 나오면 그렇게 만든다 — *"쓰지 않기로 판단하는 것도 설계입니다."*

## 2. 정상 경로 (슬라이스 1)

```
[사용자] 기획안 입력
   │  폼(지역·시기·테마·예상 방문객·규모) 또는 기획안 텍스트 붙여넣기
   ▼
[텍스트면 LLM 파싱] ── 항목이 빠졌으면 ─▶ 무엇이 없는지 짚어 되물음
   │
   ▼
[닮은 축제 탐색]  특징 벡터 → 거리 계산 → 상위 3개
   │
   ├── 닮은 축제 없음 ──▶ "비교 대상 없음 + 찾아본 범위" 로 종료
   │
   ▼
[그들의 실제 기록 조회]  예상 방문객 vs 실제 · 무너진 지점
   │
   ▼
[경보 등급 산출]  닮은 축제 중 몇 곳이 어떻게 됐나로 등급을 매긴다
   │
   ▼
[출력]  등급 · 한 문장 · 왜 닮았나(항목별) · 그들이 겪은 것(출처 포함)
```

**상태는 없다.** 한 요청이 한 번에 끝난다. 이것도 아직 에이전트가 아니라는 증거다.

## 3. 실패 경로

강의 p26: *"에이전트 설계의 대부분은 실패 설계입니다. 정상 경로는 원래 쉽습니다."*

| 이런 일이 생긴다 | 정해두지 않으면 | 이 제품의 처리 |
|---|---|---|
| **닮은 축제를 못 찾음** | 억지로 가장 가까운 걸 내놓음 | **"비교할 만한 과거 축제가 없습니다"** + 찾아본 범위 명시. 거리 임계값을 넘으면 결과에서 뺀다 |
| **닮았는데 결과 기록이 없음** | 빈칸을 그럴듯하게 채움 | **"닮았지만 결과가 기록되지 않은 축제"** 로 따로 표시. 등급 계산에서 제외 |
| **위험 근거를 못 찾음** | "안전합니다" 라고 말함 | **"판단 못 함".** 안전 판정은 하지 않는다 (암묵지 3번) |
| **외부 API 타임아웃** | 전체가 멈춤 | 1회 재시도 → 실패 시 **정적 데이터만으로 축소 응답** + "일부 확인 실패" 배지 |
| **입력이 예상을 벗어남** | 500으로 끝남 | 지역명 모호 → 후보 제시하고 되물음. 필수 항목 누락 → 무엇이 없는지 짚어 되물음 |
| **기획안 텍스트가 너무 김** | 토큰 초과로 에러 | 앞부분만 파싱하고 잘렸음을 알린다 |

## 4. 프레임워크: 쓰지 않는다

랭체인·랭그래프 없이 간다. 강의 p24 기준 판정.

| 살 만한 순간 (p24) | 이 프로젝트 |
|---|---|
| 재시도·체크포인트·중단 후 재개가 필요할 때 | 재시도 1회뿐. 한 요청이 수 초 안에 끝난다 |
| 노드가 5개를 넘고 상태가 노드 사이를 흐를 때 | 슬라이스 1은 **상태가 아예 없다** |
| 사람이 중간에 개입해야 할 때 | 되물음 1회 |

**셋 다 해당 없음 → 안 산다.** SDK 직접 호출과 함수 몇 개면 충분하고, **이 코드는 내가 읽을 수 있다.**

## 5. RAG: 쓰지 않는다

축제 기록은 **구조화된 필드**(지역·시기·테마·예상·실제·소진시점)로 들어온다. 문서를 검색해 답을 만드는 구조가 아니다. 임베딩·벡터DB·청킹이 들어갈 자리가 없다.

강의 p25가 지적한 RAG 실패 3종(문서에 답이 없음 · 청킹이 답을 자름 · 메타데이터 없어 엉뚱한 문서가 옴)이 **구조적으로 발생하지 않는다.** 기록마다 출처가 그대로 남는다.

## 6. 데이터와 도구

| 항목 | 출처 | 비고 |
|---|---|---|
| 축제 목록·개요 | **한국관광공사 TourAPI** | 지역·시기·테마의 원천 |
| 지역 인구 | 공공데이터 | 규모 대비 접근성 판단용 |
| **실제 방문객 수** | 지자체 발표·언론 보도 | ⚠️ **여기가 이 프로젝트의 급소다** — 아래 |
| 기획안 파싱 · 문장 생성 | LLM | 런타임 1회씩 |

> ⚠️ **최대 리스크 — "실제로 몇 명 왔나" 는 정형 데이터가 없다.**
> 예상치와 실제치를 함께 가진 축제 기록이 몇 건이나 모이는지가 이 제품의 생사를 가른다. **Day 2에 20건을 손으로 모아본다.** 20건이 안 나오면 쐐기를 바꾼다 — 방문객 수 대신 "물량 소진·대기 시간·민원" 같은 다른 붕괴 신호로 축을 옮긴다.
> 이 확인 전까지 나머지 계획은 전부 가정 위에 서 있다.
