#### A-1 · **CRITICAL** · "제 지역 축제를 넣었는데 아무 판정이 안 나옵니다"

**심사위원의 질문:** "함평나비축제로 넣어 봤습니다. 예상 30만, 기간도 넣었는데 1·2·3단계가 전부 '계산 불가'고 결론이 '근거 없음'입니다. 그럼 이 서비스는 군포·화천 두 개만 되는 겁니까?"

**근거(배포본 실측):**

    GET /check?name=함평나비축제&sido=전남&sigungu=함평군&n=300000&basis=period
        &counting=personDays&start=2027-04-24&end=2027-05-05
    → <strong>예상 방문객 근거 없음</strong> · 신뢰도 낮음
    → 1단계 계산 불가 / 2단계 계산 불가 / 3단계 계산 불가  (data-result="계산 불가" 3건)
    → 단서: "첫 회 축제라 자기 이력이 없다. 인구 12~30만 지역 축제 상위 5% 배수만 참고한다."

코드 분기: `lib/verdict.ts:327-353` — `requiredMult` 는 `if (last)` 안에서만 계산된다. 이력 기간이 비면 `last === null` → `requiredMult = null` → `r = null` → `multLabel = null` → `label = "근거 없음"`(`:394-400`). 즉 **지난 회차 날짜를 정확히 아는 사람만 쓸 수 있는 제품**이다.

증상이 셋으로 번진다.

- 첫 화면이 반대로 약속한다: `app/page.tsx:217` — "이력이 없는 첫 회 축제는 닮은 축제 619건의 등급이 대신 섭니다". **대신 서지 않는다.** `/check` 는 또래 구간 카드만 내고 등급은 `/`(다른 화면)에 있다.
- 1999년부터 열린 함평나비축제에 "**첫 회 축제라**"라고 단정한다(`lib/verdict.ts:352`). 실제로는 "이력 입력 없음"인데 사실 주장으로 적었다.
- `e2e.test.mjs:412-415` 가 이 동작을 **기대값으로 고정**해 놨다(`assert.match(첫회, /근거 없음|신뢰도 낮음/)`). 팀이 알고 수용한 상태다.

**잔존 경로:** ralplan §0.2 가 이미 지목했고(R-3) 해법은 **M11(첫 회 축제 요구 배수, 0.8일)** 이었다. 사용자가 고른 8일 밴드에서 잘렸다.

**수정 방향(0.6~0.8일, 새 기능 0):**

1. `checkVisitors` 에서 `last === null` 일 때도 **작년 같은 시기(기획 기간의 −364일) 베이스라인**으로 `requiredMult` 를 계산한다. KT 자료는 전국 299 시군구가 다 있으므로 새 자료가 필요 없다.
2. 비교 대상은 또래 P95, 결과는 라벨이 아니라 **별도 종류**("또래 기준 참고 — 이 축제 이력 아님")로 낸다. `Label` 유니온 7종 불변(R7) 유지.
3. `lib/verdict.ts:352` 문구를 "첫 회 축제라" → "**지난 회차 기간이 입력되지 않아**"로. 이건 5분이고, 이것만 해도 오단정 하나가 사라진다.
4. `app/page.tsx:217` 의 "619건 등급이 대신 섭니다"를 실제 동작에 맞게 고치거나, `/check` 의 이력 없음 상태에서 `/`(619건 등급)로 가는 링크를 실제로 놓는다.
5. `/check` 폼의 "지난 회차 기간" 칸 위에 **"모르면 비워 두세요 — 또래 기준으로 참고값을 냅니다"** 한 줄. 지금은 왜 비면 안 되는지가 폼 어디에도 없다.

#### A-2 · **CRITICAL** · "이 표는 0.9~1.0배라는데 옆 문장은 1.75배가 이 축제 이력이라고 합니다"

**심사위원의 질문:** "같은 A4 한 장에 '자기 이력 2025: 평균 0.9~1.0배'와 '이 축제 이력상 평균 배수 최댓값은 1.75배(2025)'가 같이 있습니다. 어느 쪽이 이 축제 실측입니까? 1.75 셀에는 공사 API 출처와 조회일까지 붙어 있는데요."

**근거(배포본 `/report/check` 인쇄 지면, 이력 1년 케이스):**

    <span class="num" data-origin="measured"
          data-source-api="DataLabService/locgoRegnVisitrDDList"
          data-source-value="1.753" data-source-period="2025" data-source-date="2026-09-09"
          title="이 축제 이력 평균 배수 최댓값 (2025) · DataLabService/… · 2025 · 조회 2026-09-09">1.75배</span>

같은 지면의 자기 이력 표: `2025 11-03~11-07 | 평균 0.93배 | 최대일 1.02배`
같은 지면의 보완 문장: "이력 배수 구간 **(최대 1.75배)** 으로 물량을 올려 잡는다"

코드: `lib/verdict.ts:344-347` — 이력이 1년이면 `historyMult = Math.max(자기값, peer.peakP95 | peer.meanP95)`. 그 뒤 `:364-373` 이 그 값을 **`origin:"measured"` · `api: KT_API` · `period: years.join(",")` · `label: "이 축제 이력 … 배수 최댓값 (2025)"`** 로 찍는다. 값의 실체는 **619건 또래의 상위 5%**인데 라벨·기간·출처는 이 축제의 것이다.

이건 팀이 이미 한 번 스스로 잡은 결함과 **같은 종류**다 — `critic_endpoints_2026-09-10.md §1 #1` 에서 "가정 예산 ÷ 실측"을 `measured` 로 찍은 것을 `derived` 로 고쳤다. 그 원칙("두 출처가 섞인 값은 measured 로 찍지 않는다. 출처 세탁이다", `HANDOFF:63`)이 여기엔 적용되지 않았다.

**수정 방향(0.2일):**

- 또래 P95 가 채택될 때는 **별도 Measured 두 개**로 낸다: `historyMultOwn`(이 축제 실측, measured) + `peerP95`(또래 619건, origin `derived`, api "한국관광 데이터랩 축제 목록 619건 재계산", period "2025~2026").
- 3단계 분모 라벨을 "**또래 상위 5% 배수 (인구 12~30만 168곳)**"로 바꾸고, `explainVisitors`·`adviseVisitors` 의 "이 축제 이력상" 조각을 분기한다.
- `lib/verdict.test.ts` 에 회귀 1건: 이력 1년 + peer 채택 시 `evidence.find(e=>e.key==="historyMult").origin !== "measured"`.

#### A-3 · **CRITICAL** · "축제가 끌어온 연인원이 마이너스 7,408명입니까"

**심사위원의 질문:** "날짜를 정확히 몰라서 대략 넣었더니 '2025 축제가 끌어온 연인원 **−7,408명**'이 한국관광공사 출처로 나오고, 결론은 '과소 — 물량을 올려 잡으라'입니다. 축제가 사람을 마이너스로 끌어옵니까?"

**근거(배포본 실측, 축제가 없던 평범한 11월 평일 5일을 이력으로 입력):**

    GET /check?sido=경기&sigungu=군포시&n=300000&basis=period&counting=personDays
        &h1s=2025-11-03&h1e=2025-11-07
    → 2단계 분모 셀: data-origin="measured" data-source-value="-7407.75"
       data-source-api="DataLabService/locgoRegnVisitrDDList"  표시 "-7,408명"
    → 최종 라벨 "과소" · 보완 "실제로 온 만큼을 감당 못 할 위험이 있다. … 물량을 올려 잡는다"
    → /report/check 인쇄 지면에도 그대로 인쇄된다 (200 확인)

`lib/verdict.ts:274-287` 이 `last.visitors` 를 **양수 검사 전에** evidence 에 넣고, `:289` 의 `denomVal > 0` 검사는 stage 의 ratio 만 막는다. 화면 셀은 이미 나갔다.

더 나쁜 것: `lib/history.ts:5` 주석이 "**잘못된 기간을 넣으면 그 해는 빠지고 이유가 남는다. 짐작해서 채우지 않는다**"라고 적혀 있는데, 실제로 빠지는 건 **자료 범위 밖**일 때뿐이다(`historyOf:60-67`). 자료 범위 안의 아무 5일이나 넣으면 축제가 없어도 배수·순증·판정이 전부 선다. 부산 해운대구에 지어낸 날짜(2025-08-01~05 / 2026-08-01~05)를 넣으니 **"주의" 판정이 정상적으로 나왔다**(실측). 이 제품의 핵심 주장은 "이 축제가 **실제로 겪은** 것"인데, 실제로 겪었는지를 아무도 확인하지 않는다.

**수정 방향(0.3~0.4일):**

1. `historyYear` 에 **축제 신호 게이트**: 입력 기간의 최대일 배수가 임계 미만이면 `skipped` 로 보내고 이유를 `"no-surge"` 로. 임계는 화면에 적는다(이미 모든 임계를 적는 제품이라 일관된다).
2. 그 전이라도 최소한 `visitors <= 0` 이면 evidence 에 **넣지 않는다**(`:274` 의 `last.visitors !== null` → `last.visitors !== null && last.visitors > 0`). 한 줄이다.
3. 게이트에 걸리면 "이 기간에는 KT 실측에서 축제 신호가 잡히지 않는다. 날짜를 확인해 달라"를 `/check` 상단 alert 로. 지금 `skipped` 안내는 사이드바 맨 아래 작은 글씨다.
4. `skipped` 사유의 **영문 내부 코드 노출**도 같이 고친다 — 배포본 실측: "자료 밖이라 뺐다 (**no-festival-days**). 적재 범위 2019-05-01~2026-08-09". 심사위원 화면에 영문 enum 이 그대로 나간다(`lib/history.ts:22`, `app/check/page.tsx:456-460`).

## 5. 열린 질문 (점수에 반영 안 함)

- **A-3 의 축제 신호 게이트 임계를 얼마로 둘 것인가.** `docs/range_backtest.md` 의 채택 필터가 최대일 배수 1.3 을 쓰므로 그 값을 재사용하면 "이미 잰 자리에서 가져온 값"이 된다. 다만 1.3 은 작은 축제를 다 걸러낼 수 있다. 619건 전량에 두어 개 임계를 걸어 보고 고르는 게 맞다(0.2일).
- **A-1 의 −364일 베이스라인이 "짐작 금지" 원칙을 깨는가.** `HANDOFF:58` 이 "이력 기간 자동 탐지 금지는 제품 입력 규칙이지 방법 검증 규칙이 아니다"라고 구분해 뒀고, A-1 은 제품 입력 쪽이라 이 예외에 안 들어간다. 다만 "이 기간은 담당자가 준 게 아니라 우리가 −52주로 잡은 것"이라고 셀에 적으면 원칙을 지키면서 빈손을 면할 수 있다고 본다. 최종 판단은 팀 몫이다.
